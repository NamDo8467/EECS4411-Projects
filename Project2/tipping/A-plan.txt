Overview: The query plan finds the top 10 highest-spending customers in
Canada who bought Romance books, by joining all three tables,aggregating sales
per customer, sorting and retunring the top 10

Access paths:
1. Sequential Scan:
- Seq Scan on book B
	Filter: genre = "Romance"
	Rows scanned: 50,000 -> keep 4625 rows
- Seq Scan on customer C
	Filter: country = "Canada"
	Rows scanned: 100,000 -> keep 74, 811
Postgres reads every single row from both table and applies the filter to keep
the matching records only. No indexes are used even though they exist.

2. Parallel Sequential Scan:
- Postgres is scanning all 10 million rows in Purchase table
- It does that by splitting the work across  workers. Each worker scans about
3.3 million rows simultaneously.

3. Hash join algorithm
- First hash join: p.bookid = b.bookid
	+ Build a hash table from 4625 Romance books
	+ Probe with Purchase rows
	+ Result: 442865 rows per worker (3 workers)

- Second hash join: p.custid = c.custid
	+ Build a hash table from 74811 Canadian customers
	+ Probe with: previous join result
	+ Result: 352638 rows per work (3 workers)
- The optimizer correctly chooses the smaller tables (Book and Customer) to
build hash tables from, and thhe larger result (Purchase) to probe with.

4. Partial Hash -> Gather -> Finalize Hash Aggregate:
- Paritial HashAggregate (per worker):
	+ Groups by: c.custid
	+ Computes: partial SUM(p.sale)
- Gather: collects results from all 3 workers
- Finalize HashAggregate:
	+ Merge partial sums into final totals
	+ Final group: 26377
- Each parallel worker computes a partial SUM for the customers it has seen.
- Since workers only see a portion of the data, their sums are imcomplete.
- The Gather node collects all partial results from all workers into one.
- Finalize HashAggregate merges the partial sums for the same customer across
different workers into a final correct total.


5. Sorting + Limit
- Sort key: (sum(p.sale)) DESC
- Sort method: top-N heapsort
- Memory: 26kB
- Limit: 10 rows
